# C1 答辩材料：10 分钟讲稿与 5 分钟问答准备

本文件是可供现场使用的材料。按用户确认，课堂环节以本材料和 [内部独立审查记录](analysis/FINAL_REVIEW.md) 交付；未实际举行课堂讲述或答辩。完整报告与复现入口见 [WRITEUP.md](WRITEUP.md)。建议配 8 页投影片；表中分钟是讲述预算，现场可优先省略次要数值，保留结论、关键反例与证据边界。

## 一、10 分钟中文讲稿

### 第 1 页，0:00–0:40：先回答题目

展示：题目、B300 平台、三条结论。

我们研究的问题是：FlashKDA 在 B300 上仍使用 SM80 世代的 MMA，这是落后于硬件，还是合理取舍？我们的结论是，现有证据支持保留 C16 和传统 MMA 作为默认实现，但不能由此排除 SM100 专版。

我们做了三类工作：复现原版和 FLA 的同语义性能；把 chunk 范围、求逆稳定性和新指令形状分别量化；最后实现 value 维度的 CTA 切分挑战。挑战正确，但六个计时形状全部负收益。接下来我解释它为什么负收益，以及哪些方向仍有机会。

### 第 2 页，0:40–1:50：算子语义与复现

展示：K1 → workspace → K2 的流程；H96 三行性能表。

KDA 先衰减旧状态，再用 key 查询旧状态，把 value 与预测的差写回，最后生成当前输出。chunk 算法把这个递推整理为矩阵乘。K1 计算与入口状态无关的内容，所以能沿 chunk 并行；K2 要读到上一个 chunk 的状态才能继续，因此一个序列、一个 head 对应一条长链。

复现中有一个很容易漏掉的语义问题。原 benchmark 没给当前 FLA 版本传 safe_gate，但 FlashKDA 使用的是 bounded sigmoid gate。我们先保留原样运行结果，再只补充 safe_gate 和现行状态布局参数，报告加速比采用后者。还设置了 FLA_FLASH_KDA=0，防止参考实现反过来调用被测内核。

在 H96、D128、总长度 8192 下，单序列、不等长六序列、八条独立短序列分别得到 1.93、2.36、2.89 倍加速；补充 H64 后，总体范围是 1.48 到 2.89 倍。这是同一 B300 上、同门函数的比较。实际扩展 SASS 出现 HMMA，未出现 HGMMA 或 UTCHMMA，所以“仍是传统 MMA”由二进制确认。

### 第 3 页，1:50–3:30：为什么是 C16？

展示：C16 / 32 / 64 的指数范围、求逆 FLOP 表；突出两个反例。

C16 有三个互相配合的理由：指数范围、求逆成本，以及 16×16 的 warp 级形状。

先看范围。当前把因果衰减拆成 exp(G_i) 和 exp(−G_j) 两个因子。每 token 最强 gate 是负五，C16 对应正负八十，仍可表示；C32 和 C64 则达到正负一百六十和三百二十。我们在 GPU 上测到第十八个 token，指数归零、逆指数变成 Inf。两者相乘得到 NaN。只把 BF16 改成 FP32 解决不了，因为它们的指数范围相近。

再看求逆。严格下三角矩阵 L 满足 L 的 C 次幂为零，所以 Neumann 在精确算术下是有限恒等式，不需要范数小于一。但有限恒等式不保证有限精度稳定。C16、32、64 的 dense 求逆每 token 成本依次是三千、一万六千、八万二千 FLOP 左右。

我们构造所有 key 同向的例子。最终逆的元素最多只有一，中间幂却按组合数增长。C16 的一个 beta 值让逆的最大误差达到一；C32 和 C64 在 P8 就溢出。更值得注意的是，全 FP32 doubling 在 C64 仍产生约二十一亿的绝对误差，而线性系统的无穷范数条件数只有一百二十八。因此需要改进求解组织，不能只提高 accumulator 精度。

这些是独立数值机制测试，不是已经完成了 C32 或 C64 的完整 KDA。

### 第 4 页，3:30–4:55：C16 是否天然排斥 tcgen05？

展示：转置映射表、最终 tile 增量表。

答案是部分不匹配，而不是整个算子都不匹配。K1 的 16×16 逆使用普通 tcgen05 时需要补到 M64，孤立形状利用率只有四分之一。但 K2 的 16×128 结果可以用乘积转置恒等式改成 128×16，五类矩阵乘都能找到合法形状。不能把 K1 的限制推广到全部 K2。

我们用 BF16 输入、FP32 累加做了 shared 输入的依赖链微基准。64 个配置均检查全部 CTA 的有限值和 CPU 参考，误差为零；实际 SASS 同时确认 HMMA 与 UTCHMMA。

在 96 CTA 下，转置后的瘦矩阵仍是 SM80 更快；128×128×16 的 state update，tcgen05 的增量成本约一百一十二纳秒，SM80 约一百九十四纳秒，有约 1.73 倍的有利信号。

但这是扣除固定成本后的整轮增量，不是单指令延迟。完整单轮 state update 微基准仍是 tcgen05 较慢。新路径有 TMEM、commit 和 wait；旧路径可由编译器复用寄存器操作数。微基准只能支持继续研究，不能替完整 K2 宣布加速。

### 第 5 页，4:55–6:10：真正的瓶颈是什么？

展示：K1 / K2 的 grid、duration、tensor elapsed / active；H96 → H12 对照。

我们没有把整个算子简单贴成 compute-bound 或 memory-bound。K1 有四万九千多个 CTA，L2 活动较高，DRAM 吞吐约 4.53 TB/s，tensor 活动较低；它还要执行门函数、归约和准备工作。

K2 则只有九十六个 CTA，少于 B300 的一百四十八个 SM。它的 DRAM 吞吐约 1.35 TB/s，tensor elapsed 比例约百分之十八，两者都没有饱和。这更符合并行覆盖不足和链内依赖限制。

最有解释力的是 TP8 对照。每卡 head 从九十六降到十二，K1 时间从约二百七十三微秒降到四十二微秒；K2 却仍约七百八十七微秒，接近原来的七百九十三微秒。head 少了八倍，单 head 的五百一十二个 chunk 依赖链没有变短。

所以 profile 必须同时看 grid、waves、active 和 elapsed 指标、shared / registers，以及等待采样。仅看到总 FLOP 不高，或者只看一个 stall 名称，都不足以给出因果结论。

### 第 6 页，6:10–7:35：我们的挑战为什么失败？

展示：value 切分示意、六行性能表、资源变化。

不同 value columns 的状态递推互不依赖，没有跨列归约，所以我们把原来同一 CTA 中的四个 compute warp，分成两个 CTA，每个保留两个 warp。这会把 K2 grid 翻倍，同时保留每列的算术顺序和 BF16 舍入点。

正确性方面，三十组精度案例、八种状态接口组合，以及三个 H96 完整长度形状均与 baseline 逐位一致。性能方面，六个正式形状全部变慢，baseline 除以候选只有约 0.57 到 0.75。我们没有把负收益隐藏起来。

NCU 说明，单纯增加 CTA 不够。这个第一版仍为每个 CTA 分配完整 shared state，输入也重复读取；寄存器从六十五增到八十，并出现 baseline 没有的 local memory 请求。K2 时间接近翻倍，tensor elapsed 比例还下降了。

这个实验的价值是明确了边界：按列并行在数学上可行，实际也能保持逐位一致；但资源和数据搬运如果不一起重构，增加 CTA 会得不偿失。它不能证明所有 value split 都失败，更不能证明官方实现是全局最优。下一步需要分别消融 shared 分配、输入复制和 store 路径。

### 第 7 页，7:35–8:55：BF16 状态精度能保证吗？

展示：三层 oracle、误差表、正交方向衰减停滞示意。

我们把实现一致性和数学精度分开。第一层官方 torch_ref 模拟相同舍入，三十组 output 和 state 全部逐位一致。第二层使用固定 FLA naive 逐 token 递推，它内部是 FP32，不把它称为 FP64 gold。第三层是同 bounded gate 的 FLA Triton chunk。

在两个 seed、五种长度组织、三类 gate 的三十组案例中，FlashKDA 相对 naive 的 output 与 state 最大相对 RMSE 都不到百分之零点七五。另补四组弱衰减长序列直到三万二千七百六十八 token，output 相对 RMSE 最大约百分之零点八二，最差一千零二十四 token 窗口的相对 RMSE 约百分之零点八二四，官方舍入参考仍逐位一致。这些是整实现误差，不能全部归因于状态 BF16。

理论上还有一个互补反例：状态落在所有 key 的正交方向，delta 更新不会碰它；每 chunk 应衰减到 0.9984，保存 BF16 却又回到一。重复保存便会停滞。这个反例来自隔离状态存储的 CPU 检查，不能说已经在完整 GPU kernel 上测出了同样值。

因此随机测试通过并不等于全输入保证。真实发布还需要长序列、低维 key、弱衰减、模型级评估，以及只改变持久状态精度的消融。外部 state dtype 改成 FP32 也不等于内部持久状态真的变成 FP32。

### 第 8 页，8:55–10:00：v2 决策与证据边界

展示：保留默认 / 条件后端 / 暂不发布三栏。

如果我们是作者，会保留当前 C16 路径，并把 SM100 专版作为条件后端继续研发，而不是发布这个 split2 版本。

保留原版的理由是已经验证的端到端收益、C16 数值范围和 warp 形状的契合，以及成熟的寄存器数据流。研究专版的理由是 K2 通过转置能够匹配新指令，state update 微基准出现有利信号，TP 后的并行覆盖不足也确实存在。

研发顺序应是先把完整 K2 的 TMEM 消费、标量更新、输入和状态布局连起来，再用完整 fwd 的精度和时间判断是否发布。大 chunk 路线则先解决指数表示和稳定求逆，不能仅因为新指令喜欢大 tile 就扩大 chunk。

最后明确我们没有证明的部分：没有完成完整 tcgen05 K2，没有模型级质量数据，也没有证明所有 SM100 路线都比原版差。我们交付的是可复现的正面证据、失败实现和反例，使下一步优化有具体依据。代码、固定版本、原始 JSON、SASS 和 NCU report 都随报告保存。

## 二、5 分钟提问准备

下面是备选题库，不需要在五分钟内主动逐项背完。建议每题先用一句话回答，再用一项证据支持；遇到未测问题明确边界。

### 1. “逆矩阵元素不超过 1，为什么还会溢出？”

有界的是最终结果，中间幂不受这个界约束。对严格下三角全 1 的 L，L^p 含组合数；C32 的部分和 P₈=I−L+L²−…−L⁷ 最大幅值为 475,020，超过 FP16 的 65,504。P₈ 与幂 L⁸ 是不同阶段。精确逆只是主对角 1、第一下对角 −1。这里的两件事并不矛盾。打开 [数值报告](analysis/C1_NUMERIC_EXPERIMENTS.md) 的阶段统计即可核对。

### 2. “全 FP32 也错，是不是 reference 或系统条件数有问题？”

β=1 的参考有简单解析式，不依赖三角求解器的可信度；κ∞=||I+L||∞||R||∞=2C，C64 只有 128。中间量约 1e17，最终要消成幅值 1，FP32 有效位不够。GPU 的 C64 最大误差约 2.15e9，说明这一路 doubling 不稳定；不能据此推断所有 FP32 三角求解都不稳定。

### 3. “为什么不直接 CHUNK=64 加 rescale？”

需要同时处理三项：指数因子范围、逆矩阵中间增长、shared / stage 容量。只中心化，C64 最坏仍有 ±160；换 FP32 不扩充指数范围；保留原 buffer 外推约 306 KiB / CTA，超容量。可以重新分块和求解，但那是完整算法重构，不能当成修改一个常量。

### 4. “M64 最小 tile 说明全部只有 25% 利用率？”

只对孤立 16×16 输出的直接 padding 成立。K2 的 16×128 乘法可以转置成 128×16，形状利用率为 100%。不过合法形状不等于满峰值，TMEM、标量操作、缓冲和同步仍有成本。请看 WRITEUP 第 5 节的映射表。

### 5. “你的 tcgen05 微基准是不是对它不公平？”

它是特定数据流的依赖链实验，不是峰值测试。我们明确报告 tcgen05 每轮 commit / wait，而 SM80 可复用寄存器操作数；也报告完整单轮和扣固定成本的增量两种数据。state update 增量 1.73× 有利，完整单轮却仍慢，所以没有把它包装成完整 KDA 加速。

### 6. “split2 更慢，为什么说明并行度重要？”

并行度不足由 H96 / H12 的 grid 与 K2 时间交叉验证，而不是由 split2 成败倒推。split2 只证明增加 CTA 的同时新增成本可能更大。这里完整 shared 分配未缩小、寄存器增多且产生 local 请求，不能把该版本等同于无成本的理想并行度增加。

### 7. “多 head 合进一个 CTA 不就填满 tile 了吗？”

它减少 CTA 数，不能改善低 NH 时的全卡覆盖；独立 head 的矩阵也不能简单拼接，否则计算出跨 head 交叉项。它可能通过交错独立链改善 CTA 内等待，但必须使用正确的批处理 / 布局并核算额外工作，不能只看填满矩形。

### 8. “为什么不把长序列切成八条？表里明显更快。”

表中八条是真实独立序列。把同一长序列重置成八个零状态段会改变语义。若要并行处理同一序列，必须计算各段入口状态，例如 affine scan；转移矩阵复合一般有 O(D³) 工作或低秩增秩成本，不能免费消除依赖。

### 9. “BF16 状态误差不到 1%，可以宣布安全了吗？”

不能。这是已列出的有限随机验证域，测量了整实现差异，而且参考 naive 为 FP32。它不覆盖所有合法输入或模型级质量。正交方向弱衰减停滞反例说明还需定向验证。真正的状态精度消融要固定其他舍入点，仅改变持久状态存储。

### 10. “性能比和 NCU 时间为什么不完全一致？”

benchmark 使用普通 CUDA event 样本，NCU detailed 会多次 replay、flush cache，并改变观测环境；两者也可能包含不同辅助工作。用 NCU counter 解释瓶颈，用同条件 benchmark 计算正式速度比，不把它们混成一张无差别计时表。

### 11. “是不是自动编译器已经把 mma.sync 换成新指令了？”

实际 `sm_103a` 扩展的反汇编有 `HMMA.16816.F32.BF16` 和 `HMMA.16816.F16`，未出现 HGMMA / UTCHMMA；自定义 tcgen05 实验则明确出现 UTCHMMA。因此这里不是仅凭 C++ 类名推断。静态实例计数不代表单次 kernel 的动态执行次数。

### 12. “你最终完成了什么、还欠什么？”

完成固定版本官方复现、同语义 FLA 对比、NCU / SASS、数值与 tile 实验、按 value 切分的真实 CUDA 挑战及其负收益报告。没有完整 tcgen05 K2、完整 C32 / C64 KDA、模型级质量评估或实际 FP32 持久状态消融；课堂环节按确认范围交付本材料及内部独立审查记录，未举行实际课堂活动。
